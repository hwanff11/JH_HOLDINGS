# JDSS Telegram Bot 운영 가이드 — 현재판

이 문서는 **운영자가 Telegram에서 무엇을 보고 어떤 버튼을 눌러야 하는지**만 설명합니다. 전략 수학은 [`STRATEGY_GUIDE.md`](STRATEGY_GUIDE.md), 정확한 주문 계약은 [`JDSS_FINAL_SPEC.md`](JDSS_FINAL_SPEC.md), 현재 배포·live 상태는 [`../CURRENT_WORK.md`](../CURRENT_WORK.md)를 따릅니다.

## 1. 평소에는 이것만 기억하면 됩니다

```text
/dashboard
  → 오늘 주문 한번에 검토
  → 화면에 나온 상태·수량·총 예상금액 확인
  → BUY가 있으면 N건 순차 실행 최종 승인
```

전략 판단·목표비중 계산·SELL 우선처리·주문수량 계산은 시스템이 담당합니다. 운영자는 **위험을 늘리는 BUY의 최종 승인**만 합니다.

현재 Oracle이 forced dry-run이면 `순차 실행`도 실제 Toss 주문이 아니라 **DRY 모의주문**입니다.

## 2. `오늘 주문 한번에 검토`가 먼저 확인하는 것

버튼을 누르면 다음 순서로 preflight를 수행합니다.

1. 현재 시간이 주문 허용 세션인지 확인
2. Toss 08:50~08:59 KST 주문 점검시간인지 확인
3. 최신 완결 거래일의 V3.2.2 계산이 끝났는지 확인
4. 새 목표라면 다음 미국 거래일이 시작됐고 target quantity가 고정됐는지 확인
5. 위험축소 SELL 또는 기존 BUY 미체결이 남았는지 확인
6. 브로커와 JDSS 원장을 즉시 reconciliation
7. SAFE_MODE 여부 확인
8. 필요한 QQQ/TQQQ/SOXL BUY를 한 화면에 모음
9. 전체 예상 BUY 합계를 HWM75·JDSS 현금·브로커 주문가능금액과 비교
10. 최종 실행 직전에 위 핵심 조건을 다시 검사

하나라도 안전하게 증명되지 않으면 BUY 버튼을 열지 않는 **fail-closed** 방식입니다.

## 3. 화면 상태 읽는 법

`BUY 신호 0건`과 `진짜 오늘 주문 없음`은 같은 뜻이 아닙니다.

| 화면 표시 | 의미 | 운영자 행동 |
|---|---|---|
| `토스 주문 점검시간` | 08:50~08:59 KST | 점검시간 종료 후 다시 확인 |
| `주문 가능시간 대기` | 설정상 주문 허용 세션이 아님 | 기다렸다가 다시 확인 |
| `전략 계산 확인 필요` | 최신 완결봉 계산이 끝나지 않음 | 주문 없음으로 해석하지 않음 |
| `다음 미국 거래일 대기` | 새 목표는 계산됐지만 주문수량 고정 시점 전 | 기다림 |
| `목표수량 생성 대기` | 거래일은 시작됐지만 target quantity가 아직 준비되지 않음 | 잠시 후 재확인 |
| `위험축소 준비 중` | 목표보다 많이 보유해 SELL 준비 필요 | BUY 시도하지 않음 |
| `매도 완료 대기` | 자동 SELL이 종료되지 않음 | 체결·정합성 완료까지 대기 |
| `매수신호 생성 대기` | 목표보다 부족하지만 BUY 승인 신호 준비 전 | 잠시 후 재확인 |
| `기존 매수 진행 중` | 이미 BUY 주문이 열려 있음 | `미체결 주문 보기` 확인 |
| `계좌/원장 불일치` | reconciliation 실패 | `/errors` 확인, 새 BUY 금지 |
| `최초진입 단계 대기` | 현재 50%/75% 목표는 채웠고 다음 단계 대기 중 | `/onboarding` 안내 확인 |
| `오늘 주문 없음` | 최신 계산·목표·정합성까지 확인했고 실제 보유가 목표와 일치 | 아무것도 하지 않아도 됨 |

## 4. BUY만 필요한 날

예: QQQ +5주, TQQQ +3주가 필요하다면 다음 정보를 한 화면에 보여줍니다.

- 전략 기준일
- 종목별 주문수량
- 종목별 지정가와 예상금액
- 총 예상 BUY 금액
- 현재 HWM75 기반 매수가능한도
- JDSS 현금
- 정합성 확인 결과

그 아래에 **`오늘 모의매수 2건 순차 실행`** 같은 최종 버튼이 표시됩니다.

`순차 실행`은 basket 주문 하나가 아닙니다. 각 종목이 독립 주문으로 제출되므로 첫 주문 뒤 시장·수량·현금 조건이 달라지면 일부 종목만 제출되고 나머지는 중단될 수 있습니다.

이미 제출된 앞 주문을 시스템이 자동 반대매매해 되돌리지 않습니다. 실제 주문상태를 계속 추적합니다.

## 5. SELL 후 BUY가 필요한 날

예를 들어 SOXL을 줄이고 TQQQ를 늘려야 하면 다음 순서를 강제합니다.

```text
SOXL 위험축소 SELL 자동 제출
  → SELL 종료 확인
  → 체결 원장 반영
  → broker/DB reconciliation
  → 이상 없음
  → TQQQ BUY 후보 생성
  → 오늘 주문 한번에 검토
  → 운영자 최종 승인
```

SELL이 `SUBMITTED`, `PARTIAL_FILLED`, `PENDING_CANCEL`, `PENDING_REPLACE`, `UNKNOWN` 등 종료 전 상태이면 신규 BUY를 열지 않습니다.

## 6. 최종 버튼을 눌렀을 때 다시 확인하는 것

검토 화면을 본 뒤에도 계좌와 시세가 바뀔 수 있으므로 최종 클릭 순간 다시 검사합니다.

- 즉시 reconciliation
- SAFE_MODE
- 새로 생긴 미체결 주문
- 전체 HWM75/현금/브로커 주문가능금액
- 각 종목 가격·수량·세션
- execution approval TTL과 1회성

가격·수량·세션이 달라졌다면 이전 화면 그대로 주문하지 않고 **새로운 검토를 요구**합니다.

## 7. 순차 실행 중 실패하면

예를 들어 QQQ 주문은 제출됐지만 TQQQ에서 가격변경 오류가 발생했다면:

1. QQQ 주문은 실제 상태로 계속 추적
2. TQQQ 주문은 제출하지 않음 또는 실패 상태로 기록
3. 그 뒤 SOXL 등 남은 BUY 중단
4. 남은 approval 취소
5. `미체결 주문 보기`와 `/errors`에서 확인

Telegram 결과 메시지가 전송되지 않더라도 batch 생성·차단·실행·부분실패 이벤트는 시스템 감사로그에 남깁니다.
`/errors`와 오류 알림에는 운영 판단에 필요한 요약만 표시하며 credential, 외부 URL, 서버 절대경로와 장문 식별번호는 자동으로 가립니다. 원본 traceback은 접근 통제된 Oracle 로그에서 확인합니다.

## 8. 중복 클릭과 오래된 버튼

- batch 검토 생성과 실행은 lock으로 직렬화
- 유효한 batch가 이미 있으면 두 번째 검토가 새 batch를 만들지 않음
- execution approval은 짧은 TTL과 1회용
- 이미 사용·취소·만료된 callback 재사용 금지
- 서버가 재시작되면 과거 메모리 batch 버튼으로 주문하지 않고 최신 검토 요구
- onboarding 버튼도 생성 당시 단계와 현재 DB 단계가 다르면 stale 버튼으로 거부

## 9. 최초진입 50% → 75% → 100%

`/onboarding`은 **매수 주문 버튼이 아니라 누적 목표 한도를 여는 기능**입니다.

| 단계 | 최종 전략 목표 대비 누적 한도 | 다음 단계 조건 |
|---|---:|---|
| 1차 | 50% | 현재 단계 전량 체결 + 최소 3 미국 거래일 |
| 2차 | 75% | 현재 단계 전량 체결 + 최소 3 미국 거래일 |
| 3차 | 100% | 전량 체결 시 onboarding 완료 |

예를 들어 `1차 매수 한도 열기 · 50%`를 눌러도 즉시 BUY가 제출되지는 않습니다. 단계가 열린 뒤 `/today` 또는 `오늘 주문 한번에 검토`에서 필요한 BUY를 묶어 확인하고 최종 승인합니다.

현재 단계 목표를 이미 채웠다면 전체 100% 목표와 비교해 `매수신호 누락`으로 표시하지 않고 **현재 단계 완료 / 다음 단계 대기**로 안내합니다.

## 10. 개별 BUY 경로

`/signal`과 `개별 매수 보기`는 비상용·상세 확인 경로로 유지됩니다.

```text
매수 주문 검토하기
  → 최신 가격·수량 계산
  → 종목 N주 모의/실매수 실행
```

일상 운영에서는 일괄 검토를 우선하고, **일괄 batch가 열린 상태에서 같은 신호를 개별 승인으로 동시에 처리하지 않습니다.**

## 11. 미체결 주문 상태

| 상태 | 의미 | 운영자 행동 |
|---|---|---|
| `CREATED` / `SUBMITTED` / `PENDING` | 주문 진행 중 | 중복 주문 금지, 계속 감시 |
| `PARTIAL_FILLED` | 일부 체결 | 잔여 상태를 시스템이 추적 |
| `FILLED` | 전량 체결 | 원장 반영·정합성 확인 |
| `CANCELED` / `REJECTED` / `REPLACED` | 정상 전량체결이 아님 | `/today`, `/order`, `/errors` 확인 |
| `UNKNOWN` | 주문 결과를 증명할 수 없음 | 성공 추정·재주문 금지, SAFE_MODE 확인 |

## 13. 사용자용 용어

Telegram에서는 내부 구현명보다 다음 표현을 우선합니다.

| 내부·과거 표현 | 사용자 화면 표현 |
|---|---|
| allocation | 목표비중 조정 / 보유·목표 |
| overlay | 추가 레버리지 / 추가매수 판단 |
| 위험증가 BUY | 매수 필요 / 매수 승인 대기 |
| batch | 오늘 주문 묶음 / 순차 실행 |
| reconciliation | 계좌·원장 정합성 확인 |

내부 코드·DB 키는 안정성을 위해 기존 이름을 유지할 수 있지만 사용자 메시지에 불필요한 개발 용어를 그대로 노출하지 않습니다.

## 14. forced dry-run과 live

현재 정확한 운용 모드는 [`../CURRENT_WORK.md`](../CURRENT_WORK.md)를 확인합니다.

forced dry-run에서는:

- 주문·보유·미체결은 SQLite + 모의 브로커 기준
- `/account`는 실제 Toss 계좌를 조회만 함
- dry-run 주문이 실제 Toss 주문으로 변환되지 않음
- read-only 조회 성공이 live 주문 검증을 뜻하지 않음

실제 Toss 주문 활성화는 별도 preflight와 명시적 승인이 필요한 별개의 변경입니다.

## 15. 문제가 생겼을 때

1. 같은 버튼을 반복해서 누르지 않습니다.
2. `/order`에서 열린 주문을 확인합니다.
3. `/errors`에서 batch·reconciliation·SAFE_MODE 이벤트를 확인합니다.
4. `UNKNOWN` 또는 불일치가 있으면 성공으로 추정하거나 재주문하지 않습니다.
5. forced dry-run인지 live인지 추측하지 말고 `CURRENT_WORK.md`와 봇 잠금 표시를 확인합니다.
6. 원인이 불명확하면 신규 BUY보다 SAFE_MODE 유지가 우선입니다.

## 16. 매일 아침 운용 브리핑 읽는 법

정규장 종료 후 일일 계산이 완료되면 V3.2.2 내부 이벤트를 그대로 나열하지 않고 **한 개의 운영자용 아침 브리핑**으로 묶어 표시합니다. 첫 화면에서 먼저 `오늘의 결론`을 보고, 필요할 때 아래 세부 항목을 읽는 구조입니다.

표시 순서는 다음과 같습니다.

1. `오늘의 결론` — 신규 매수 승인 필요 여부 또는 위험축소 진행 여부
2. `현재 목표 비중` — QQQ/TQQQ/SOXL 최종 목표비중
3. `전략 판단` — 시장상태, 목표 노출, 반도체 상대강도, 추가 레버리지 상태
4. `쉽게 말하면` — 내부 지표를 사용자 관점의 한두 문장으로 해석
5. `자금관리` — 현재 평가액, 최고 평가액, HWM75 투자규모 계산 기준
6. `/today`, `/portfolio` 바로가기 안내

아침 브리핑의 `지금 승인할 신규 매수 주문은 없습니다`는 해당 일일 계산 시점에 즉시 승인할 BUY가 없다는 뜻입니다. 주문 가능시간·미체결 상태·정합성은 계속 변할 수 있으므로 실제 주문 여부의 최종 판단은 `/today`가 담당합니다.

위험축소 이벤트가 함께 발생한 날은 신규매수 안내보다 **위험축소 매도 진행 상태를 우선 표시**합니다. 매도와 계좌·원장 정합성 확인이 끝날 때까지 신규 BUY를 열지 않는 기존 안전 규칙은 변경하지 않습니다.

`RS6M`, `allocation`, `위험예산`, `완결종가 평가액` 같은 내부 표현은 일일 브리핑 첫 화면에서 최소화하고 각각 `반도체 상대강도`, `현재 목표 비중`, `투자규모 계산 기준`, `현재 평가액`처럼 운영자가 바로 이해할 수 있는 용어로 표시합니다.
