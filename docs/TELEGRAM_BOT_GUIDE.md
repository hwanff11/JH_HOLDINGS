# JDSS Telegram Bot 운영 가이드 — 현재판

이 문서는 Telegram에서 JDSS V3.2.2를 실제로 확인하고 주문하는 방법을 설명합니다. 전략 수학은 `STRATEGY_GUIDE.md`, 정확한 주문·최초진입 계약은 `JDSS_FINAL_SPEC.md`, 현재 개발·배포 상태는 `CURRENT_WORK.md`를 따릅니다.

## 1. 평소 사용법

평소에는 `/dashboard`에서 **`오늘 주문 한번에 검토`**를 누르면 됩니다.

시스템이 확인하는 순서는 다음과 같습니다.

1. 최신 완결 거래일의 V3.2.2 전략 계산이 실제로 끝났는지 확인합니다.
2. 목표가 새로 바뀐 날이면 다음 미국 거래일이 시작되어 고정 목표수량이 만들어졌는지 확인합니다.
3. 위험축소 SELL이나 기존 BUY 미체결이 남아 있는지 확인합니다.
4. 실제 브로커 상태와 JDSS 원장을 즉시 reconciliation(정합성 대조)합니다.
5. SAFE_MODE가 아닌지 확인합니다.
6. 오늘 필요한 QQQ/TQQQ/SOXL BUY를 한 화면에 모읍니다.
7. 전체 예상금액이 HWM75 위험예산·JDSS 현금·브로커 주문가능금액을 함께 반영한 실제 매수가능한도 안인지 확인합니다.
8. 운영자가 **`오늘 모의매수 N건 순차 실행`** 또는 향후 승인된 live의 **`오늘 실매수 N건 순차 실행`**을 누르면 각 종목을 순서대로 제출합니다.
9. 최종 버튼을 누르는 순간 정합성·매수가능한도·가격·수량·세션을 다시 확인합니다.

즉 전략 판단과 주문수량 계산은 자동이고, 위험축소 SELL은 자동이며, 위험을 늘리는 BUY만 사람이 최종 승인하는 반자동 구조입니다.

현재 Oracle은 **forced dry-run**이고 live는 잠겨 있습니다. 따라서 현재의 순차 실행은 실제 Toss 매수가 아니라 DRY 모의주문입니다.

## 2. 화면 상태를 구분해서 읽기

`오늘 주문`은 단순히 BUY 신호가 없다고 해서 바로 “주문 없음”이라고 표시하지 않습니다.

| 표시 | 의미 |
|---|---|
| `전략 계산 확인 필요` | 최신 완결봉 계산이 끝나지 않았거나 지연됨. 주문 없음으로 간주하지 않음 |
| `다음 미국 거래일 대기` | 새 목표비중은 계산됐지만 실제 주문수량을 확정할 다음 거래일이 아직 시작 전 |
| `목표수량 생성 대기` | 다음 거래일은 시작됐지만 고정 목표수량 생성이 아직 끝나지 않음 |
| `위험축소 준비 중` | 목표보다 많이 보유한 종목이 있어 자동 SELL 생성/처리를 기다리는 상태 |
| `매도 완료 대기` | SELL이 이미 제출됐으며 전량 종료 전까지 BUY 차단 |
| `매수신호 생성 대기` | 목표수량보다 부족하지만 BUY 승인 신호 생성이 아직 끝나지 않음 |
| `기존 매수 진행 중` | 이미 BUY가 제출돼 중복 주문을 차단한 상태 |
| `계좌/원장 불일치` | 즉시 정합성 점검 실패. 신규 BUY 차단 |
| `오늘 주문 없음` | 최신 계산·고정 목표·정합성을 모두 확인했고 목표수량과 보유수량이 실제로 일치 |

따라서 장애나 계산 지연을 “살 것이 없다”라고 잘못 판단하지 않도록 상태를 분리합니다.

## 3. BUY만 필요한 날

예를 들어 QQQ 5주와 TQQQ 3주가 부족하면 한 화면에 다음 내용을 표시합니다.

- 전략 기준일
- QQQ/TQQQ/SOXL별 주문수량·지정가·예상금액
- 총 예상 매수금액
- 현재 HWM75 매수가능한도
- 현재 JDSS 현금
- 즉시 정합성 확인 결과

그 아래 **`오늘 모의매수 2건 순차 실행`** 버튼이 표시됩니다.

`순차 실행`은 하나의 원자적 basket 주문이 아닙니다. QQQ → TQQQ → SOXL 순으로 각각 독립 주문을 제출합니다. 앞 주문 뒤 조건이 달라지면 일부 주문만 제출되고 나머지는 자동 중단될 수 있습니다. 이미 제출된 앞 주문을 시스템이 임의로 되돌렸다고 가정하지 않습니다.

## 4. SELL 후 BUY가 필요한 날

목표비중 변경으로 어떤 종목은 줄이고 다른 종목은 늘려야 하면 다음 순서를 강제합니다.

1. 위험축소 SELL 자동 제출
2. SELL 전량 완료 확인
3. 체결을 JDSS 원장에 반영
4. 브로커/원장 정합성 확인
5. 이상이 없을 때만 BUY 후보 생성
6. `오늘 주문 한번에 검토`
7. 운영자 최종 승인 후 BUY 순차 제출

SELL이 `SUBMITTED`, `PARTIAL_FILLED`, `PENDING_CANCEL`, `UNKNOWN` 등 종료 전이면 BUY 버튼을 만들지 않습니다. SELL 실패·불완전·결과 불명은 SAFE_MODE 규칙을 따릅니다.

## 5. 일괄 주문 안전장치

### 한도 확인

각 종목이 개별적으로 살 수 있어 보여도 합계가 위험예산을 넘을 수 있으므로, 최종 버튼을 만들기 전에 **전체 예상 BUY 합계**를 HWM75·현금·브로커 주문가능금액을 함께 반영한 매수가능한도와 비교합니다. 초과하면 일부 종목을 임의로 줄여 주문하지 않고 전체 검토를 중단합니다.

### 동시 클릭·오래된 버튼

Telegram이 threaded 방식으로 처리되더라도 일괄 검토 생성과 최종 실행은 하나의 lock으로 직렬화합니다. 이미 유효한 검토가 있으면 두 번째 검토는 새 approval을 만들지 않습니다.

최종 승인은 짧은 TTL을 가지며 만료·취소·사용 후에는 다시 사용할 수 없습니다. 서버가 재시작되면 메모리에 있던 batch도 폐기되므로 과거 메시지 버튼은 거부되고 최신 조건으로 다시 검토해야 합니다.

### 최종 실행 직전 재검증

검토 후 Toss 앱 등 외부에서 보유수량이나 주문상태가 바뀔 수 있으므로 최종 버튼 직전에 reconciliation을 다시 수행합니다. 정합성 실패, SAFE_MODE, 새 미체결 주문, 매수가능한도 감소가 확인되면 한 종목도 새로 제출하지 않고 batch를 취소합니다.

### 순차 제출 중 실패

예를 들어 QQQ는 제출됐지만 TQQQ에서 가격·수량 변경 또는 `UNKNOWN`/`REJECTED`/`CANCELED`가 발생하면 TQQQ 이후 주문을 중단하고 남은 approval을 취소합니다. 앞서 제출된 QQQ는 자동 rollback하지 않으며 `미체결 주문 보기`와 `/errors`에서 실제 상태를 확인합니다.

batch 검토 생성·만료·취소·실행 시작·실행 결과는 시스템 이벤트로 기록하므로 Telegram 결과 메시지 전송에 문제가 생겨도 `/errors`에서 감사기록을 확인할 수 있습니다.

## 6. 자동 알림과 개별 주문

스케줄러가 QQQ/TQQQ/SOXL BUY 후보를 여러 개 만들더라도 종목별 승인 카드를 반복 전송하지 않고 **`오늘 매수 검토 가능` 한 장**으로 묶어 알립니다. 최초진입 단계에서도 같은 방식을 사용합니다.

기존 `/signal`과 `개별 매수 보기`는 비상용·상세 확인 경로로 유지합니다. 개별 경로는 `매수 주문 검토하기` → 최신 조건 재계산 → `종목 N주 모의/실매수 실행`의 기존 2단계 승인입니다.

일괄 검토와 개별 승인을 동시에 진행하지 않는 것이 기본 운영 원칙입니다. 이미 일괄 검토가 열려 있다면 그 검토를 실행하거나 취소한 뒤 다른 경로를 사용합니다.

## 7. 최초진입 50% → 75% → 100%

`/onboarding`은 새 계좌가 한 번에 전액 진입하지 않도록 매수 가능한 누적 한도만 단계적으로 엽니다.

| 단계 | 최종 목표 대비 누적 한도 | 다음 단계 조건 |
|---|---:|---|
| 1차 | 50% | 현재 단계 목표수량 전량 체결 후 최소 3 미국 거래일 |
| 2차 | 75% | 현재 단계 목표수량 전량 체결 후 최소 3 미국 거래일 |
| 3차 | 100% | 전량 체결 시 최초진입 완료 |

`1차 매수 한도 열기 · 50%` 같은 버튼은 주문을 제출하지 않고 한도만 엽니다. 단계가 열린 뒤 `오늘 주문 한번에 검토`에서 그 단계에 필요한 BUY를 묶어 승인할 수 있습니다.

오래된 단계 버튼의 **callback**에는 버튼 생성 당시 단계번호가 들어 있고 현재 DB 단계와 다르면 거부합니다. 과거 메시지를 다시 눌러도 단계가 중복 상승하지 않습니다.

## 8. 주문 상태 읽기

| 상태 | 뜻 | 운영자 행동 |
|---|---|---|
| `CREATED`·`SUBMITTED`·`PENDING` | 접수됐지만 끝나지 않음 | `미체결 주문 보기`에서 계속 확인 |
| `PARTIAL_FILLED` | 일부 체결 | 주문 모니터가 잔여 상태를 감시; 중복 주문 금지 |
| `FILLED` | 전량 체결 | 원장 반영과 다음 정합성 확인 |
| `CANCELED`·`REJECTED`·`REPLACED` | 정상 전량체결이 아님 | 최신 목표·`/today`·`/errors` 확인 |
| `UNKNOWN` | 제출 결과를 증명할 수 없음 | 성공으로 추정하거나 재주문하지 말고 SAFE_MODE 확인 |

주문 감시·정합성 점검·안전 경고는 기존 주기로 계속 수행합니다.

## 9. 주요 명령과 실거래 잠금

| 명령 | 기능 |
|---|---|
| `/dashboard` | 통합 대시보드와 주요 버튼 |
| `/today` | 오늘 주문 한번에 검토 |
| `/portfolio` | 자산·현금·위험한도·목표/현재 비중 |
| `/onboarding` | 최초진입 50→75→100 단계 |
| `/account` | 실제 Toss 계좌 read-only 조회 |
| `/status [종목]` | 종목별 목표·보유·주문 상태 |
| `/score [TQQQ|SOXL]` | 추가매수 판단 점수 |
| `/signal` | 개별 매수 승인 대기 |
| `/order` | 미체결 주문 |
| `/errors` | 최근 시스템 이벤트·batch 감사기록·SAFE_MODE 원인 |
| `/backtest` 또는 `/bt` | production V3.2.2 포트폴리오 백테스트 |
| `/ping` | 운영 모드와 실주문 잠금 확인 |

미국 정규장 마감 뒤 일일 목표비중·분석은 한국시간 오전 7시 이후 생성합니다. `/today`는 이미 계산된 production 목표를 안전하게 주문으로 연결할 뿐, 버튼을 눌러 전략 신호 자체를 임의 변경하지 않습니다.

Toss 주문 API 어댑터가 존재하는 것과 실주문이 활성화됐다는 것은 별개입니다. 현재 V3.2.2는 **forced dry-run / live LOCKED OFF**이며 Telegram 버튼만으로 live를 활성화할 수 없습니다.
