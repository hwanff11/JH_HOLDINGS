# JDSS Telegram Bot 운영 가이드 — 현재판

이 문서는 Telegram 명령 문법, 화면에 표시되는 데이터의 출처, 버튼·승인 흐름과 오류 대응의 소유 문서입니다. 다음 릴리즈에서도 새 파일을 만들지 않고 코드의 명령 등록·`/help`·메시지 포맷 테스트와 함께 이 파일을 갱신합니다.

현재 배포·운용 모드는 [`CURRENT_WORK.md`](../CURRENT_WORK.md), 전략 설명은 [`STRATEGY_GUIDE.md`](STRATEGY_GUIDE.md), 정확한 주문·최초진입 계약은 [`JDSS_FINAL_SPEC.md`](JDSS_FINAL_SPEC.md)를 따릅니다.

## 1. 가장 중요한 네 가지

1. 현재 봇은 허용된 관리자와의 **1:1 private chat**에서만 명령과 버튼을 처리합니다.
2. 매수는 사람이 `매수 주문 검토하기`와 `최종 매수 실행`을 각각 누르는 **반자동 2단계 승인**입니다.
3. 위험을 줄이는 SELL은 자동 실행 대상이지만, 현재 forced dry-run에서는 BUY와 SELL 모두 모의주문입니다. `/account`의 실제 Toss 조회와 혼동하지 않습니다.
4. 최초 진입은 `/onboarding`에서 **50% → 75% → 100%**로 단계적으로 열며, 오래된 단계 버튼은 현재 DB 단계와 다르면 거부합니다.

## 2. 화면에서 쓰는 용어

운영 화면은 내부 개발 용어보다 실제 행동이 바로 보이도록 표시합니다.

| 화면 표현 | 뜻 |
|---|---|
| `목표비중` | 전략이 현재 계좌에서 보유하려는 종목별 비율 |
| `현재 보유비중` | JDSS 원장 기준으로 현재 실제 보유 중인 비율 |
| `보유/목표` | 해당 종목의 목표비중·현재수량·열린 주문·안전상태 확인 |
| `추가매수 판단` | TQQQ/SOXL 점수를 이용해 QQQ 일부를 추가 레버리지로 바꿀지 판단하는 보조 입력 |
| `매수 주문 승인 대기` | 전략 목표를 채우기 위해 운영자의 매수 승인을 기다리는 주문 후보 |
| `위험한도` | HWM75 규칙으로 현재 전략이 투자에 사용할 수 있는 위험예산 |

`추가매수 판단`은 TQQQ/SOXL을 별도로 무조건 사라는 신호가 아닙니다. V3.2.2 최종 목표비중 안에서 QQQ 최대 5%를 TQQQ/SOXL 쪽으로 조정할지 계산하는 보조 신호입니다.

## 3. 화면별 데이터 출처

| 표시 | 데이터 출처 | 의미 |
|---|---|---|
| `/dashboard`, `/portfolio`, `/status`, `/order`, `/signal` | SQLite JDSS 원장 + 현재 주문 브로커 | 목표·보유·주문·승인 상태 |
| `/onboarding` | SQLite 최초진입 상태 + 현재 목표수량 | 1회성 50→75→100 단계, 체결·대기일·다음 단계 가능 여부 |
| `/score`, `/history` | 완결 일봉과 H40-S3 분석 | TQQQ/SOXL 추가매수 판단용 점수이며 독립 직접매수 신호가 아님 |
| `/account` | 실제 Toss OpenAPI read-only | 실제 계좌 조회이며 모의원장에 자동 반영하지 않음 |
| `/backtest` | production과 공유하는 전략·포트폴리오 백테스트 경로 | 실제 주문이나 현재 보유수량을 사용하지 않는 과거 시뮬레이션 |
| `/errors` | SQLite 이벤트 로그 | 최근 오류·SAFE_MODE·운영 경고 |

`/account`가 정상이라고 dry-run reconciliation이 실제 Toss와 끝난 것이 아니고, dry-run이 정상이라고 실제 Toss 계좌가 전략 적용 준비를 마친 것도 아닙니다.

미국 정규장 마감 뒤 생성되는 일일 목표비중·분석·신호 알림은 서머타임과 무관하게 **한국시간 오전 7시 이후** 실행합니다. 30초 scheduler poll 안에서 시작하므로 통상 07:00~07:01 사이에 전송되며, 데이터 조회 지연이 있으면 더 늦어질 수 있습니다. 주문 감시·정합성 점검·안전 경고는 기존 1분 주기로 계속 수행합니다.

## 4. 명령과 대시보드 버튼

| 명령 | 무엇을 보여주나 |
|---|---|
| `/ping` | 봇 버전·운영 모드·실주문 잠금 |
| `/dashboard` | 자산·위험한도·목표/현재 보유비중·매수 주문 승인 대기 |
| `/portfolio` | 평가액·현금·위험한도·QQQ/TQQQ/SOXL 목표/현재 비중 |
| `/account` | 실제 Toss 주문가능금액·보유종목 read-only 조회 |
| `/status [QQQ|TQQQ|SOXL]` | 종목별 목표비중·원장수량·열린 주문·안전상태 |
| `/onboarding` | 최초진입 상태, 현재 단계, 목표수량, 대기 거래일, 다음 단계 버튼 |
| `/score [TQQQ|SOXL]` | TQQQ/SOXL 추가매수 판단 점수·시장국면·활성 후보 |
| `/history [TQQQ|SOXL] [1~90]` | 최근 추가매수 판단 점수 이력; 기본 7거래일 |
| `/signal` | 현재 유효한 매수 주문 승인 대기 |
| `/backtest` 또는 `/bt` | 최초진입 50→75→100을 포함한 production 포트폴리오 백테스트 |
| `/order` | 현재 미체결 주문 |
| `/errors` | 최근 시스템 이벤트와 SAFE_MODE 원인 |
| `/guide` | 현재 전략 요약 카드 |
| `/help` | 현재 명령과 대표 사용 예시 |

`/dashboard` 아래 버튼은 다음처럼 사용합니다.

- `QQQ/TQQQ/SOXL 보유/목표`: 해당 종목의 목표와 현재 상태를 바로 확인합니다.
- `TQQQ/SOXL 추가매수 판단`: 추가 레버리지 점수를 바로 확인합니다.
- `매수 승인 대기 보기`: `/signal`을 입력하지 않고 현재 매수 후보를 버튼으로 불러옵니다.
- `미체결 주문 보기`: `/order`를 입력하지 않고 주문 진행 상태를 버튼으로 확인합니다.

최초진입 별칭은 `/entry`, `/firstentry`입니다. 그 밖에 `/p`, `/d`, `/pf`, `/acct`, `/st`, `/sc`, `/h`, `/sg`, `/bt`, `/o`, `/err`, `/g` 등의 짧은 별칭도 사용할 수 있지만 운영 기록과 문서에서는 기본 명령을 우선합니다.

## 5. 최초진입 `/onboarding`

최초 적용 시 전략의 최종 목표비중과 HWM75 위험예산은 그대로 두고, 매수 한도만 한 번에 전부 열지 않습니다.

| 단계 | 최종 전략 목표 대비 누적 한도 | 다음 단계 조건 |
|---|---:|---|
| 1차 | 50% | 현재 단계 목표수량 전량 체결 후 최소 3 미국 거래일 |
| 2차 | 75% | 현재 단계 목표수량 전량 체결 후 최소 3 미국 거래일 |
| 3차 | 100% | 전량 체결 시 최초진입 완료 |

조건이 맞으면 `1차 매수 한도 열기 · 50% (주문 전)` 버튼이 표시됩니다. 단계 버튼은 **매수 가능한 한도만 열 뿐 주문을 제출하지 않습니다.** 다음 단계도 자동으로 열리지 않습니다.

단계를 연 뒤 실제 종목별 BUY는 다음 순서입니다.

1. `종목 매수 주문 검토하기`
2. 최신 가격·남은 목표수량·현금·허용 세션 재계산
3. 최종 지정가·수량·예상수수료 확인
4. `종목 N주 모의매수 실행` 또는 별도 live 승인 릴리즈의 `종목 N주 실매수 실행`
5. 주문번호·처리상태·체결수량 Telegram 회신

시장 악화로 목표가 줄면 위험축소 SELL은 단계 대기보다 먼저 자동 실행합니다. 각 단계 버튼의 **callback에는 버튼 생성 당시 단계번호를 함께 넣고**, 현재 DB 단계와 다르면 오래된 버튼으로 판단해 거부합니다. 따라서 과거 메시지의 callback을 다시 눌러도 단계가 중복 상승하지 않습니다.

3차 완료 뒤에는 최초진입 상태가 영구 완료되어 일반 V3.2.2 운용으로 전환됩니다.

## 6. BUY 버튼과 주문 확인

시스템이 완결봉과 현재 목표 차이로 매수가 필요하다고 판단하면 Telegram에 매수 승인 카드를 보냅니다.

1. `매수 주문 검토하기`는 주문 버튼이 아니라 **1차 확인 버튼**입니다.
2. 버튼을 누르면 현재가·추격상한·남은 목표수량·현금·시장 세션을 다시 계산합니다.
3. 최종 화면에는 지정가·수량·투자금액·예상수수료가 표시됩니다.
4. 사람이 종목과 수량이 적힌 `모의매수 실행` 또는 향후 승인된 `실매수 실행` 버튼을 눌러야 주문이 제출됩니다.
5. 최종 버튼은 짧은 유효시간을 가지며, 가격·수량·세션이 달라지면 기존 승인을 폐기하고 다시 확인합니다.
6. 제출 후 Telegram이 주문번호·상태·체결수량을 보여줍니다. 미체결이면 대시보드의 `미체결 주문 보기` 버튼이나 `/order`에서 계속 확인합니다.

현재 forced dry-run에서 최종 버튼이 제출하는 것은 `DRY-*` 모의주문입니다. **실제 Toss 주문 API 어댑터가 구현돼 있다는 사실과 현재 실주문이 활성화돼 있다는 것은 서로 다른 의미입니다.** 현재 live 잠금은 유지됩니다.

### 위험축소 SELL

목표비중 감소는 승인 버튼을 기다리지 않고 자동 실행합니다. 한 조정에 SELL과 BUY가 함께 있으면 SELL을 먼저 종료·원장 반영·정합성 확인한 뒤 BUY 승인 신호를 만듭니다.

- SOXL→TQQQ 전환: SOXL 축소 SELL은 자동, 새 TQQQ 증가 BUY는 2단계 승인
- SELL이 부분체결·UNKNOWN·취소확인 실패: 신규 BUY 차단 및 SAFE_MODE
- 주문 상태가 `PENDING_CANCEL`·`PENDING_REPLACE` 등 종료 전이면 계속 열린 주문으로 표시

## 7. 주문 메시지 읽기

| 표시 상태 | 뜻 | 운영자 행동 |
|---|---|---|
| `PENDING`·`SUBMITTED`·`CREATED` | 접수됐지만 완료되지 않음 | `미체결 주문 보기` 또는 `/order`로 계속 확인 |
| `PARTIAL_FILLED` | 일부만 체결 | 남은 수량을 주문 모니터가 감시; 중복 승인 금지 |
| `FILLED` | 전량 체결 | 원장 반영과 다음 reconciliation 확인 |
| `CANCELED`·`REJECTED`·`REPLACED` | 전량 완료가 아님 | `/signal`, `/order`, `/errors`로 재승인 가능 여부 확인 |
| `UNKNOWN` | 제출 결과를 증명할 수 없음 | 성공으로 추정·재주문하지 말고 SAFE_MODE 확인 |

같은 알림이 반복 폭주하지 않도록 동일 오류는 일정 시간 묶어서 알릴 수 있습니다. 알림이 줄어도 오류가 해결됐다는 뜻은 아니므로 `/errors`의 최신 기록을 봅니다.

## 8. `/backtest` 사용법

Telegram 백테스트는 임의 종목 단독 시험이 아니라 **현재 production V3.2.2 전체 포트폴리오 경로**를 실행합니다. 요청한 보고 시작일은 빈 계좌의 최초진입일로 간주하며, 결정론적 백테스트에서는 1~3번째 미국 거래세션에 최종 목표의 50%, 4~6번째에 75%, 7번째부터 100%를 적용합니다.

| 입력 | 기간 |
|---|---|
| `/bt` | 최신 완결 거래일까지 최근 300거래일 |
| `/bt 250` | 최신 250거래일; 2~5,000 범위 |
| `/bt full` 또는 `/bt all` | 설정의 기준 시작일부터 최신 완결 거래일까지 |
| `/bt 2020-01-01 2024-12-31` | 입력한 시작일~종료일 |

날짜는 `YYYY-MM-DD`, 시작일은 설정의 기준 시작일 이상, 종료일은 최신 완결 거래일 이하여야 합니다. 장기 canonical 검증은 Telegram보다 GitHub Actions를 우선합니다.

## 9. SAFE_MODE 대응

다음과 같은 상황은 신규 매수를 차단합니다.

- SQLite와 현재 주문 브로커의 보유수량·열린 주문 불일치
- 주문결과 `UNKNOWN` 또는 broker order ID 누락
- 위험축소 SELL 불완전·취소 미확정
- 누적 부분체결과 원장 적용 delta 불일치
- 구버전 direct position·TP plan·직접 BUY 신호 잔존

확인 순서는 `/errors` → `미체결 주문 보기`/`/order` → `보유/목표`/`/status [종목]` → `/portfolio`입니다. 실제 Toss 상태는 `/account`에서 별도로 확인합니다. 원인을 모른 채 DB를 수정하거나 같은 BUY를 다시 승인하지 않습니다.

실제 Toss 계좌 preflight에서 관리 티커 보유·열린 주문·조회 실패가 발견되면 향후 live 적용 검토를 중단합니다. read-only 실계좌 점검과 현재 dry-run 원장 SAFE_MODE는 적용 범위가 다르므로 하나의 통과 결과로 합치지 않습니다.

## 10. live 잠금과 계좌 주의사항

실제 Toss 주문 기능을 켜는 일은 Telegram 문구 변경이나 일반 배포와 별개입니다.

- 현재 정확한 모드는 `CURRENT_WORK.md`와 `/ping`에서 확인합니다.
- 현재는 설정 live OFF, 애플리케이션 hard lock과 Oracle forced dry-run을 함께 유지합니다.
- 실제 Toss 주문 어댑터는 구현돼 있지만 V3.2.2 live 실행은 별도 릴리즈 전까지 잠겨 있습니다.
- 실제 live 전환 전에는 기존 보유·열린 주문·주문가능금액, DB migration, 부분체결·재시작·reconciliation 전체 사이클을 별도로 검증합니다.
